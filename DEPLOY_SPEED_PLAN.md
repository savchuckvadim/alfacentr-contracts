# Ускорение деплоя Alfacentr

Ветка `refactor/fast-deploy`. Цель — любой деплой за 10 минут и без падений
на таймауте buildkit.

## Итог

Код в ветке готов и проверен локально. Образы собирает GitHub Actions и кладёт
в GHCR, сервер только скачивает их и перезапускает контейнеры. Фронт переведён
на standalone-сборку Next. `.env` больше не вшивается в образы.

Перед мержем нужна разовая подготовка сервера, она описана ниже. Без неё
первый деплой пройдёт, но откатиться будет не на что.

## Почему было 40–70 минут

Замер по логу упавшего деплоя 2026-09-25 (коммит `d90d0a2`), сборка фронта:

| Шаг | Время |
|---|---|
| `pnpm install --prod --no-frozen-lockfile` в финальной стадии фронта | 13 мин 17 с |
| Экспорт образа фронта | 5 мин 4 с |
| Итог: таймаут сессии buildkit | деплой упал |

По истории деплоев:

| Что менялось в коммите | Длительность |
|---|---|
| только `apps/front` | 2–4 мин |
| `packages/*` вместе с back и front | 40–70 мин |

`packages/alfa` менялся в 9 из 14 коммитов с июня. Любая его правка сбрасывала
слой установки в финальной стадии фронта, поэтому медленный путь был обычным.

Ещё две проблемы старого workflow:

- **Всё собиралось на прод-сервере.** Медленный диск, нестабильный npm,
  залипающий buildkit-билдер, сборка back и front по очереди.
- **Ложный таймаут.** Если образ бэка не менялся, compose не пересоздавал
  контейнер. Скрипт ждал смены id контейнера и падал через 15 минут при
  здоровом бэке. Так упал деплой 2026-09-25.

## Что сделано в ветке

| Файл | Изменение |
|---|---|
| `apps/front/next.config.js` | `output: 'standalone'`. Убраны проверка и блок env с `ONLINE_API_KEY`: код их не читает, а standalone вписал бы ключ в `server.js` |
| `docker/Dockerfile.front` | Финальная стадия копирует готовый standalone и ничего не ставит. Удалена мёртвая стадия `prod-deps` |
| `docker/Dockerfile.back` | `.env` не копируется в образ |
| `docker/*.dockerignore` | `apps/*/.env` вырезаны из контекста сборки |
| `docker-compose.yml` | Образы из GHCR с тегами `API_TAG` и `FRONT_TAG` из корневого `.env`. `apps/back/.env` монтируется с сервера в `/app/.env` |
| `docker-compose.build.yml` | Новый. Сборка на своей машине или аварийно на сервере |
| `.github/workflows/deploy-alfa-prod.yml` | Переписан целиком, схема ниже |

### Как работает новый деплой

1. **Что изменилось.** Изменения считаются от git-тега `prod-deployed`, то есть
   от последнего успешного деплоя. Изменения упавших и отменённых запусков
   поэтому не теряются. Тега нет — это первый запуск, собираются оба сервиса.
2. **Сборка.** Back и front собираются параллельно на раннерах GitHub, с кешем
   слоёв. Бэк собирается только при правке `apps/back`, `packages/alfa` или
   общих манифестов. Правка фронтовых пакетов его больше не трогает.
3. **Выкатка.** Сервер скачивает образ по sha коммита, перезапускает контейнер
   и ждёт, пока тот не заработает именно на новом образе и не станет healthy.
   Для фронта затем идёт смоук-тест: POST на `/api/app` должен вернуть 303 на
   `/bitrix/main`, а сама страница должна отвечать 200.
4. **Откат.** Если сервис не поднялся или не прошёл смоук-тест, скрипт сам
   возвращает прежнюю версию. Тег `prod-deployed` при этом не сдвигается.
5. **Отметка.** После успеха sha пишется в `API_TAG` / `FRONT_TAG` корневого
   `.env`, прежняя версия — в `*_PREV`. Тег `prod-deployed` переносит
   отдельная job: только у неё есть право записи в репозиторий.
6. **Уборка.** На сервере остаются образы текущей и предыдущей версии каждого
   сервиса, остальные образы alfacentr удаляются. Чужие стеки не трогаются.

Вход в GHCR делается во временном `DOCKER_CONFIG`. Вход других проектов в
`~/.docker/config.json` не затрагивается. На сервер уходит токен, который
умеет только читать пакеты этого репозитория, и живёт он, пока идёт job.

Деплои идут строго по одному и по порядку (`concurrency` с `queue: max`).
Перезапуск старого запуска не откатит прод: сервер откажется выкатывать коммит
старее уже выкаченного.

Ключ `queue: max` есть в документации GitHub, но локальный actionlint его
пока не знает. Если GitHub на первом пуше отвергнет workflow как невалидный,
деплой просто не начнётся, и достаточно удалить эту строку.

### Что проверено локально

| Проверка | Результат |
|---|---|
| Размер образа фронта | 2,06 ГБ → 281 МБ |
| Размер образа бэка | 1,68 ГБ → 466 МБ |
| Фронт: старт standalone-сервера | 0,4 с |
| Фронт: POST `/api/app` | 303, `Location: /bitrix/main` |
| Фронт: страницы, статика, шрифты, `/api/metrics` | 200 |
| Фронт: в бандле боевой режим | `IS_PROD` = true |
| Фронт: ключей и `.env` в образе | нет |
| Бэк без `.env` | падает на старте: нет `MAIL_HOST` |
| Бэк с подмонтированным `.env` | стартует, redis подключён, `/api/health` 200 |
| Бэк: CORS из подмонтированного файла | разрешённые домены проходят, чужой нет |
| Скрипт выкатки: первый деплой, повтор того же образа | успех, redis не пересоздаётся |
| Скрипт выкатки: образ с зелёным healthcheck, но 500 на `/api/app` | смоук-тест ловит, откат на прежнюю версию |
| Защита от перезапуска старого запуска | старый коммит отклоняется, повтор последнего проходит |
| shellcheck серверного скрипта | без замечаний |
| actionlint | одно замечание: не знает `queue: max` |

Не проверено: реальный прогон в GitHub Actions и скорость скачивания из GHCR
на сервер. GHCR с сервера доступен: там уже работают образы
`ghcr.io/savchuckvadim/april-*`.

Ожидаемое время, это оценка, а не замер:

| Сценарий | Сейчас | После |
|---|---|---|
| правка только фронта | 2–4 мин | 3–5 мин |
| правка `packages/alfa` + back + front | 40–70 мин | 5–8 мин |
| правка только бэка | 5–20 мин | 3–5 мин |

Первый запуск без кеша займёт дольше, ориентировочно 10–15 минут.

## Разовая подготовка сервера перед мержем

Все команды выполняются в `/var/www/html/alfacentr`.

**1. Проверить архитектуру и версию Compose.** Образы собираются под x86_64.

```
uname -m
docker compose version
```

Ожидается `x86_64` и Compose v2.

**2. Сохранить текущие образы как точку отката.** Первый деплой откатится на них,
если что-то пойдёт не так.

```
docker tag alfacentr-api:prod   ghcr.io/savchuckvadim/alfacentr-api:pre-ghcr
docker tag alfacentr-front:prod ghcr.io/savchuckvadim/alfacentr-front:pre-ghcr
printf '\nAPI_TAG=pre-ghcr\nFRONT_TAG=pre-ghcr\n' >> .env
```

Старый `docker-compose.yml` эти переменные не читает, так что до мержа они ни на
что не влияют.

**3. Убедиться, что `apps/back/.env` на месте и в нём есть новый домен в `CORS_ORIGIN`.**
Теперь бэк читает этот файл напрямую, без пересборки.

## Выкатка

1. Смержить `refactor/fast-deploy` в `main` и запушить.
2. В Actions запустится «Deploy Alfacentr prod». Тега `prod-deployed` ещё нет,
   поэтому соберутся и выкатятся оба сервиса.
3. Проверить:

```
curl -s -o /dev/null -D - -X POST https://alfa.front.april-app.ru/api/app | grep -i location
grep -E '^(API|FRONT)_TAG' /var/www/html/alfacentr/.env
docker ps --format '{{.Names}}  {{.Image}}  {{.Status}}' | grep alfacentr
```

Ожидается `location: /bitrix/main`, теги с sha коммита и оба контейнера healthy.
После этого открыть приложение в карточке сделки.

## Откат

**На предыдущую версию, без доступа к GHCR.** Её образ остаётся на сервере:

```
# в корневом .env заменить значение API_TAG на значение API_TAG_PREV
docker compose up -d --no-deps api-alfacentr
```

Для фронта то же с `FRONT_TAG` и `front-alfacentr`.

**На версию старше.** Вписать в `API_TAG` sha нужного коммита и скачать образ:

```
docker compose pull api-alfacentr
docker compose up -d --no-deps api-alfacentr
```

Образ `:<sha>` есть только у коммитов, где сервис пересобирался. Пакеты GHCR
приватные, поэтому `pull` может попросить вход: `docker login ghcr.io` с PAT,
у которого есть `read:packages`. Можно и сделать пакеты публичными: секретов в
образах нет, а код репозитория и так открыт.

Перезапуск старого запуска в GitHub Actions для отката не подходит: деплой
откажется выкатывать коммит старее уже выкаченного.

**Аварийная сборка на сервере**, если GitHub недоступен:

```
docker compose -f docker-compose.yml -f docker-compose.build.yml build api-alfacentr
docker compose up -d --no-deps api-alfacentr
```

## Правка настроек бэка

`apps/back/.env` на сервере теперь подключается в рантайме:

```
nano apps/back/.env
docker restart nest-api-alfacentr
```

Пересборка не нужна.

## Уборка через неделю стабильной работы

```
docker rmi alfacentr-api:prod alfacentr-front:prod
rm -rf ~/.alfacentr-deploy
```

Образы `pre-ghcr` удалятся сами после второго успешного деплоя каждого сервиса.
Buildx-билдер `buildx_buildkit_mybuilder0` старому деплою больше не нужен.
Перед удалением проверить через `docker buildx ls`, не пользуются ли им другие
проекты на сервере.

## Что рассматривали и не стали делать

**Распил монорепо на два репозитория.** Для скорости даёт ноль: фронту всё равно
нужны 10 общих пакетов. 7 из 9 правок `packages/alfa` с июня задевали и back, и
front. После распила `@alfa/entities` пришлось бы публиковать как npm-пакет с
версиями, и каждая сквозная правка стала бы тремя релизами.

**Общий код папками внутри приложений.** Для фронтовых пакетов возможно, но они
менялись 4 раза с июня. `alfa` пришлось бы дублировать: рантайм-код из неё нужен
обоим приложениям, фронту 31 имя в 50 файлах, бэку 44 имени.

**Типы через orval вместо `@alfa/entities`.** Заменит максимум 14 типов. 31
рантайм-имя (enum, функции, данные) останется в `alfa`, а генерация потребует
поднятого бэка в CI. Существующий `packages/nest-api` сейчас нигде не
импортируется.

**Статический фронт без Node (`output: 'export'`).** Технически возможен: фронт
по факту SPA. Но это 8–12 часов работы, переделка страницы участника и перенос
маршрутизации в nginx. По сравнению со standalone он выигрывает 2–5 минут.
Вернуться к нему стоит, если GHCR окажется медленным или захочется убрать
Node-контейнер фронта совсем.

**React внутри Nest.** Каждая правка фронта пересобирала бы образ бэка, то есть
связь стала бы теснее, а не слабее.

## Замечено по ходу, отдельные задачи

- **Redis открыт наружу без пароля.** Порт `${ALFA_REDIS_PORT}` опубликован на
  хост, а опубликованные Docker порты обходят ufw. В redis лежат очередь
  генерации документов и реестр операторов бота. Стоит закрыть порт или
  поставить пароль.
- **Данные redis в анонимном томе.** `up` их сохраняет, `docker compose down`
  теряет. Переход на именованный том — только с переносом `/data/dump.rdb`.
- **`apps/back/storage` есть только на сервере.** Там шаблон ППК-заявки. Нужен
  бэкап.
- **Легаси-файлы.** Корневые `Dockerfile`, `TestDockerfile`, `deploy.yml`,
  `docker-compose-full.yml` (с паролем MySQL в git), `docker-compose-test.yml`,
  а также `apps/back/Dockerfile` и `apps/back/docker-compose.yml`. Последний
  задаёт контейнер `redis` на порту 6334 — это имя чужого стека на сервере.
  Всё это не используется и путает.
- **Неиспользуемые зависимости фронта.** `@workspace/nest-api` и `@workspace/pbx`
  не импортируются. Их удаление меняет lock-файл.
- **Node 20.** Поддержка закончилась 30.04.2026. Оба Dockerfile на `node:20`.
- **Слой `apt-get install openssl` в Dockerfile бэка.** Остался от Prisma,
  которой в проекте нет.
