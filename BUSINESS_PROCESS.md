# Описание бизнес-процесса: Система регистрации и обработки семинаров Alfacentr

## 1. Общая концепция системы

Система **Alfacentr** представляет собой комплексное решение для автоматизации процесса регистрации клиентов на образовательные мероприятия (семинары, ППК, УП) и последующей генерации всех необходимых юридических документов. Система полностью интегрирована с CRM Bitrix24 и работает как встраиваемый модуль.

---

## 2. Начало процесса: Регистрация через форму

### 2.1. Публичная форма регистрации

**Где находится:** Внешняя форма на сайте компании (не входит в данное приложение, но является точкой входа)

**Что происходит:**
1. Пользователь (физическое или юридическое лицо) заполняет форму регистрации на семинар
2. В форме указывается:
   - **Общая информация о заказчике:**
     - ФИО или наименование организации
     - ИНН (для юридических лиц)
     - Контактные данные (телефон, email)
     - Тип клиента (физическое лицо, ИП, организация, бюджетная организация, адвокат)

   - **Информация об участниках:**
     - ФИО каждого участника
     - Номера телефонов участников
     - Email участников
     - Выбор мероприятий, на которые хочет пойти каждый участник
     - Дополнительные поля (формат участия, нужен ли ППК и т.д.)

3. Пользователь отправляет форму

### 2.2. Создание сделки в Bitrix24

**Что происходит после отправки формы:**
1. Форма отправляет данные в Bitrix24 через API
2. В Bitrix24 автоматически создается **сделка** (Deal)
3. Все поля из формы заполняются в соответствующие поля сделки
4. К сделке привязывается **компания** (если указан ИНН) или создается новый контакт

**Важно:** На этом этапе данные уже находятся в CRM, но еще не обработаны системой Alfacentr.

## 3. Первый этап автоматизации: Webhook "On Deal Init"

### 3.1. Триггер процесса

**Эндпоинт:** `POST /seminar/create-deal/:dealId`

**Когда срабатывает:** Bitrix24 отправляет webhook в приложение сразу после создания сделки

**Что получает система:**
- ID созданной сделки
- Домен Bitrix24 портала
- Токен авторизации
- Все данные сделки

### 3.2. Анализ полей сделки

**Что делает система:**

1. **Получение структуры полей:**
   - Система запрашивает у Bitrix24 все поля сделки
   - Получает их типы, названия, Bitrix ID
   - Создает маппинг между внутренними кодами полей и Bitrix ID

2. **Извлечение значений:**
   - Система читает все заполненные поля сделки
   - Преобразует их в структурированный формат
   - Определяет, какие данные относятся к участникам, какие к компании, какие к товарам

### 3.3. Поиск и добавление товаров

**Категории товаров:**
- **Семинар** - обычные семинары
- **ППК** - Профессиональная переподготовка и повышение квалификации
- **УП** - Управление проектами (два разных вида)
- **Семинар+ППК** - комбинированные программы

**Процесс:**
1. Система анализирует выбранные участниками мероприятия
2. Для каждого мероприятия ищет соответствующий товар в каталоге Bitrix24
3. Находит товары по названию или специальному полю ("ПРЕФИКС")
4. Автоматически добавляет найденные товары в товарные позиции сделки
5. Связывает товары с участниками (кто на какой семинар идет)

**Особенности:**
- Товары могут быть разных категорий (Семинар, ППК, УП)
- Один участник может выбрать несколько товаров
- Система автоматически определяет, какие товары нужно добавить

### 3.4. Создание участников в CRM (Smart Process)

**Что такое Smart Process:**
- Это специальные сущности в Bitrix24 CRM (аналог сделок, но для участников)
- Каждый участник становится отдельной записью в Smart Process
- У участников есть свои стадии жизненного цикла
- К участникам привязываются автоматизации

**Процесс создания:**
1. Система извлекает данные о каждом участнике из полей сделки
2. Для каждого участника (до 10 участников) создается запись в Smart Process
3. Заполняются поля участника:
   - ФИО
   - Телефон
   - Email
   - Выбранные товары/семинары
   - Формат участия
   - Нужен ли ППК
   - Связь со сделкой (parentId2)

4. Устанавливается начальная стадия: `NEW` (новый участник)
5. Категория: `PARTICIPANT`

**Стадии участника:**
- `NEW` - новый участник
- Другие стадии определяются автоматизациями Bitrix24 (например: "Подтвержден", "Пришел на семинар", "Не пришел", "Нужно отправить удостоверение")

**Автоматизации:**
- После создания участника могут срабатывать автоматизации Bitrix24
- Например: отправка приглашения, напоминание о семинаре, создание задач менеджеру

### 3.5. Поиск и связывание компании

**Процесс:**
1. Система извлекает ИНН из полей сделки
2. Ищет в Bitrix24 компании с таким же ИНН
3. Если компания найдена:
   - Создает запись в Timeline сделки с ссылками на найденные компании
   - Менеджер может увидеть, что компания уже существует в CRM
4. Если компания не найдена - ничего не происходит (компания будет создана позже или уже создана)

### 3.6. Создание Timeline записи

**Что такое Timeline:**
- Это история событий в сделке Bitrix24
- Показывает все действия, комментарии, изменения

**Что создается:**
1. Форматированный комментарий с информацией о сделке
2. Список всех участников с их данными
3. Информация о товарах
4. Ссылки на найденные компании (если есть)

**Результат:** Менеджер видит в сделке полную информацию о том, что произошло при автоматической обработке.

## 4. Второй этап: Работа менеджера в интерфейсе

### 4.1. Открытие сделки менеджером

**Что видит менеджер:**
- В Bitrix24 появляется новая сделка
- К сделке привязаны: компания (или контакт), участники (Smart Process), товары
- В Timeline есть информация о том, что система автоматически обработала данные

### 4.2. Открытие React модуля

**Как открывается:**
- Менеджер открывает сделку в Bitrix24
- В сделке есть специальная вкладка или кнопка "Обработка документов"
- Открывается React приложение, встроенное в Bitrix24 через iframe

**Что происходит при открытии:**
1. Приложение получает данные о текущей сделке через Bitrix24 JS SDK
2. Загружает данные о компании, пользователе, домене
3. Инициализирует WebSocket соединение для real-time обновлений
4. Начинает загрузку данных о сделке

### 4.3. Загрузка данных о сделке

**Эндпоинты, которые вызываются:**

1. **`POST /seminar/get-deal-values/:dealId`**
   - Получает все значения полей сделки
   - Преобразует их в структурированный формат
   - Возвращает данные для отображения

2. **`POST /seminar/get-fields-data`**
   - Получает структуру полей сделки
   - Возвращает маппинг полей и их Bitrix ID
   - Кэшируется в Redis на 10 минут для оптимизации

3. **`GET /alfa-bx-products/by-id/:productId`** (для каждого товара)
   - Получает детальную информацию о товарах
   - Загружает все поля товаров из каталога

### 4.4. Визуализация и проверка данных

**Что видит менеджер в интерфейсе:**

1. **Панель проверки:**
   - Система автоматически подсвечивает, чего не хватает
   - Показывает процент заполненности данных
   - Указывает на ошибки или неполные данные

2. **Информация об участниках:**
   - Красиво оформленная таблица участников
   - Статистика: сколько участников, кто на какой семинар идет
   - Связи между участниками и товарами
   - Статусы участников (из Smart Process)

3. **Информация о товарах:**
   - Таблица товаров с детальной информацией
   - Категории товаров (Семинар, ППК, УП)
   - Связи с участниками

4. **Реквизиты клиента:**
   - Отображаются реквизиты компании или физического лица
   - Показывается процент заполненности
   - Подсвечиваются незаполненные поля

### 4.5. Автоматическое определение типа договора

**Как это работает:**
1. Система анализирует все товары в сделке
2. Определяет категории товаров:
   - Если есть товары категории "Семинар" и "ППК" → тип договора: `seminar_ppk`
   - Если есть только "ППК" → тип договора: `ppk`
   - Если есть только "Семинар" → тип договора: `seminar`
   - Если есть "УП" → тип договора: `up`

3. Автоматически устанавливает тип договора в интерфейсе
4. Менеджер может вручную изменить тип, если нужно

**Логика определения:**
```typescript
if (есть товары "Семинар+ППК") → seminar_ppk
else if (есть товары "ППК") → ppk
else if (есть товары "Семинар") → seminar
else if (есть товары "УП") → up
```

### 4.6. Редактирование данных менеджером

**Что может редактировать менеджер:**

1. **Товары:**
   - Добавлять товары
   - Удалять товары
   - Изменять количество
   - Связывать товары с участниками

2. **Участники:**
   - Редактировать данные участников
   - Добавлять участников
   - Удалять участников
   - Изменять выбранные семинары для участников

3. **Реквизиты клиента:**
   - Заполнять недостающие реквизиты
   - Исправлять ошибки в реквизитах
   - Выбирать тип клиента (если не определен)

**Как сохраняются изменения:**
- Изменения сразу сохраняются в Bitrix24 через API
- Обновляется состояние в Redux store
- Интерфейс обновляется в реальном времени

### 4.7. Работа с реквизитами

**Откуда берутся реквизиты:**
1. **Из сделки** - если реквизиты уже были заполнены в форме
2. **Из компании** - если компания найдена в CRM, реквизиты берутся оттуда
3. **Из локального хранилища браузера** - система запоминает последние использованные реквизиты
4. **Из CRM** - можно выбрать сохраненные реквизиты компании из Bitrix24

**Сохранение реквизитов:**
1. **В локальное хранилище браузера:**
   - При заполнении реквизиты автоматически сохраняются в localStorage
   - При следующем открытии сделки реквизиты подтягиваются автоматически
   - Это ускоряет работу менеджера

2. **В CRM (Bitrix24):**
   - Менеджер может сохранить реквизиты в карточку компании
   - Реквизиты сохраняются в специальные поля компании
   - При следующей работе с этой компанией реквизиты будут автоматически подтягиваться

**Типы реквизитов:**
- **Основные реквизиты** (название, ИНН, КПП, ОГРН и т.д.)
- **Адрес** (юридический адрес, почтовый адрес)
- **Банковские реквизиты** (расчетный счет, корр. счет, БИК, банк)

**Валидация:**
- Система проверяет корректность заполнения реквизитов
- Показывает процент заполненности
- Подсвечивает ошибки

### 4.8. Получение номера документа

**Эндпоинт:** `POST /document-number/by-prefix`

**Когда вызывается:**
- Когда менеджер готов генерировать документы
- Система автоматически определяет префикс на основе типа договора
- Менеджер может вручную указать префикс

**Процесс:**
1. Система отправляет запрос с префиксом (например, "ППК", "СП-123456")
2. Запрос попадает в очередь `DOCUMENT_NUMBER_BY_PREFIX`
3. Система ищет или создает счетчик в списке Bitrix24
4. Инкрементирует счетчик
5. Возвращает номер документа через WebSocket

**WebSocket событие:** `document-number:done`
- Клиент получает номер документа в реальном времени
- Номер отображается в интерфейсе
- Менеджер видит готовый номер для документов

**Особенности:**
- Номера генерируются с префиксами
- Каждый префикс имеет свой счетчик
- Номера уникальны и последовательны

## 5. Третий этап: Генерация документов

### 5.1. Подготовка к генерации

**Что проверяет менеджер перед генерацией:**
- Все ли данные заполнены
- Правильно ли определен тип договора
- Корректны ли реквизиты
- Есть ли номер документа
- Все ли участники правильно привязаны к товарам

**Что видит менеджер:**
- Превью договора (что будет в договоре)
- Список товаров
- Список участников
- Реквизиты клиента и поставщика
- Итоговую сумму

### 5.2. Отправка запроса на генерацию

**Эндпоинт:** `POST /document-generate`

**Что отправляется:**
- Все данные сделки
- Реквизиты клиента
- Реквизиты поставщика
- Тип договора
- Тип клиента
- Данные участников
- Товары
- Номер документа
- Настройки email (нужно ли отправлять, кому)

**WebSocket соединение:**
- При отправке запроса устанавливается WebSocket соединение
- Передается `socketId` для получения обновлений

### 5.3. Процесс генерации (в очереди)

**Что происходит в фоне:**

1. **Задача попадает в очередь `DOCUMENT`:**
   - Используется Bull Queue с Redis
   - Задача обрабатывается асинхронно
   - Не блокирует работу системы

2. **Генерация DOCX документов:**
   - Система выбирает шаблон договора на основе типа договора
   - Заполняет шаблон данными из запроса
   - Использует библиотеку `docxtemplater` для подстановки значений
   - Генерирует документы:
     - Договор (соответствующий типу)
     - Счет (с печатью или без, в зависимости от типа клиента)
     - Акт оказанных услуг

3. **Конвертация в PDF:**
   - DOCX документы конвертируются в PDF
   - Используется LibreOffice или внешний сервис
   - PDF документы готовы для отправки

4. **Генерация ППК заявки (если нужно):**
   - Если тип договора `ppk` или `seminar_ppk`
   - Генерируется специальная заявка на ППК
   - Заявка содержит данные участников
   - Сохраняется в Bitrix24

5. **Отправка документов в Bitrix24:**
   - Все сгенерированные файлы загружаются в Bitrix24
   - Прикрепляются к сделке
   - Создаются записи в Timeline

6. **Отправка Email (если нужно):**
   - Если указано `email.needEmail = true`
   - Формируется письмо с документами
   - Отправляется через Bitrix24 API
   - Клиент получает документы на email

7. **WebSocket уведомление:**
   - Отправляется событие `document-generate:done`
   - Клиент получает информацию о результате
   - Менеджер видит статус генерации в реальном времени

### 5.4. Результат генерации

**Что получает менеджер:**
- Все документы прикреплены к сделке в Bitrix24
- В Timeline есть запись о генерации
- Если был запрошен email - клиент получил документы
- WebSocket уведомление о завершении

**Что получает клиент (если был запрошен email):**
- Договор в PDF
- Счет в PDF
- Акт в PDF
- ППК заявка (если применимо)

## 6. Дополнительные процессы

### 6.1. Обработка участников после семинара

**Что происходит:**
- Участники могут прийти на семинар или нет
- Менеджер отмечает в Smart Process, кто пришел
- Статус участника меняется

**Автоматизации:**
- Если участник прошел ППК - нужно отправить удостоверение
- Система может автоматически создавать задачи на отправку удостоверений
- Участники могут получать удостоверения по email

### 6.2. Интеграция с аудиозвонками (будущее)

**Планируется:**
- Робот будет звонить участникам
- Собирать дополнительную информацию
- Класть информацию в CRM
- Обновлять данные участников

**Примечание:** Этот функционал еще не реализован, но архитектура системы позволяет его добавить.

## 7. Итоговая схема процесса

```
1. Форма регистрации
   ↓
2. Создание сделки в Bitrix24
   ↓
3. Webhook → On Deal Init
   ├─ Анализ полей
   ├─ Поиск товаров
   ├─ Добавление товаров в сделку
   ├─ Создание участников (Smart Process)
   ├─ Поиск компании
   └─ Создание Timeline записи
   ↓
4. Менеджер открывает сделку
   ↓
5. Открытие React модуля
   ├─ Загрузка данных сделки
   ├─ Загрузка товаров
   ├─ Загрузка участников
   └─ Загрузка реквизитов
   ↓
6. Визуализация и проверка
   ├─ Автоопределение типа договора
   ├─ Подсветка недостающих данных
   └─ Статистика участников и товаров
   ↓
7. Редактирование менеджером
   ├─ Редактирование товаров
   ├─ Редактирование участников
   └─ Заполнение реквизитов
   ↓
8. Получение номера документа (WebSocket)
   ↓
9. Генерация документов
   ├─ Генерация DOCX
   ├─ Конвертация в PDF
   ├─ Генерация ППК заявки
   ├─ Отправка в Bitrix24
   ├─ Отправка Email
   └─ WebSocket уведомление
   ↓
10. Документы готовы
    ├─ В сделке Bitrix24
    ├─ Отправлены клиенту (если нужно)
    └─ Менеджер видит результат
```

## 8. Ключевые особенности системы

1. **Полная автоматизация** - от регистрации до генерации документов
2. **Real-time обновления** - через WebSocket
3. **Умная обработка** - автоматическое определение типов, поиск товаров, создание участников
