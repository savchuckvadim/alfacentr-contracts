# Архитектура: фронт, бэкенд, очереди, вебхуки

Монорепозиторий на pnpm и turbo. Два приложения и общие пакеты.

## Состав

| Часть | Что это |
|---|---|
| `apps/front` | Next.js, модуль работы с заявкой, встраивается в Битрикс как приложение |
| `apps/back` | NestJS: приём вебхуков Битрикса, очереди, генерация документов, письма |
| `packages/alfa` | сущности и общие правила предметной области: типы договоров, префиксы, участники |
| `packages/bitrix` | клиент REST API Битрикса по домену: сделки, смарты, списки, товарные позиции |
| `packages/ui` | компоненты интерфейса |

## Как связаны с Битриксом

Битрикс вызывает бэкенд **исходящими вебхуками из бизнес-процессов**: инициация заявки, выравнивание нумератора, генерация документов. Бэкенд ходит в Битрикс **входящим вебхуком** портала, ключ и домен лежат в переменных окружения.

Фронт работает внутри iframe Битрикса и часть запросов делает сам, часть через бэкенд.

## Очереди

Долгие операции идут через Bull на Redis: выдача номера документа, генерация документов, отправка писем. Очередь нужна не для скорости, а для последовательности: одновременная обработка одной сделки ломала бы данные.

Результат прилетает на фронт по WebSocket: фронт подписывается, бэкенд шлёт событие по `socketId`.

## Что важно помнить

Вебхук из бизнес-процесса — **выстрел без ответа**. Битрикс не ждёт результата и продолжает выполнять процесс дальше. Если бизнес-процесс после вебхука что-то записывает в карточку, он перезапишет то, что записал бэкенд. Поэтому вебхук ставится последним шагом ветки.

`lists.element.update` **перезаписывает элемент списка целиком**: непереданные поля очищаются. Передавать нужно все поля, а не только изменённое.
