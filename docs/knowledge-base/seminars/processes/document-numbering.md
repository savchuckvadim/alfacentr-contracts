# Нумерация договоров

Каждый договор получает номер вида «префикс + порядковый номер»: например, `СЗ2309СП 21`. Префикс определяет товар, номер — порядок внутри этого префикса.

## Откуда берётся префикс

Префикс лежит в названии товара после маркера `[]`:

```
Семинар РАЗРЕЗОВА 23-24 сентября Санкт-Петербург []СЗ2309СП
                                                  ^^^^^^^^ префикс
```

Приложение берёт префикс у первого товара сделки по приоритету: семинар, затем ППК, затем УП. То есть у сделки «семинар + ППК» префикс будет семинарный.

Префикс чистится автоматически: обрезаются пробелы по краям, неразрывные пробелы заменяются обычными, невидимые символы удаляются. Это важно, потому что `СЗ2309СП ` с пробелом на конце и `СЗ2309СП` — для системы это был бы разный префикс со своим отдельным счётчиком.

## Где хранятся счётчики

Все счётчики лежат в универсальном списке **«Договор» (ID 46)**. Один элемент списка = один префикс:

| Поле | Что в нём |
|---|---|
| Название | сам префикс, например `СЗ2309СП` |
| Активен | `Да` для рабочих счётчиков |
| Номер | последний выданный номер |

Открыть: Компания → Списки → Договор.

## Как выдаётся номер

Когда менеджер открывает сделку и в ней есть товары, приложение запрашивает номер:

1. определяет префикс по товарам;
2. **берёт блокировку на этот префикс** — чтобы два менеджера одновременно не получили один номер;
3. ищет счётчик;
4. увеличивает его на единицу и записывает обратно;
5. подставляет номер в поля сделки «Префикс» и «Номер текущего договора».

Блокировка держится только на время выдачи номера, доли секунды. Если Битрикс в этот момент недоступен, запрос повторяется три раза; если не вышло — номер **не выдаётся**, и менеджер видит ошибку. Так сделано намеренно: лучше показать ошибку, чем выдать номер, который уже есть у другого договора.

## Две системы и один счётчик

Исторически номера выдают две разные системы:

- **старый смарт-процесс «Семинары»** — нумератор собран в бизнес-процессе Битрикса;
- **новые сделки** — нумератор в приложении.

Они обязаны пользоваться одним и тем же элементом списка 46, иначе каждая начнёт считать от единицы и номера совпадут.

Тонкость в том, что бизнес-процесс ищет счётчик не в списке, а **через другую карточку смарта с тем же префиксом**: берёт у неё поле `LIST_ID` и работает с указанным элементом. Не найдя такой карточки, он создаёт свой элемент списка с номером 1.

Поэтому приложение специально ищет счётчик тем же способом:

1. сначала — карточка смарта с этим префиксом и заполненным `LIST_ID`;
2. только если её нет — элемент списка по названию;
3. и если нет ничего — создаёт счётчик.

## Первая карточка «Семинаров» по семинару, который начали заявки

Сделок бизнес-процесс не видит. Поэтому, если семинар первыми начали оформлять через новые заявки, первая карточка в «Семинарах» по нему не найдёт соседей, заведёт лишний счётчик и поставит себе номер 1. Это ожидаемо и исправляется само за несколько секунд:

1. бизнес-процесс сообщает приложению вебхуком, что завёл счётчик;
2. приложение выдаёт карточке следующий номер из общего счётчика;
3. записывает его в карточку и перенаправляет её на общий счётчик;
4. лишний счётчик помечает «Активен: Нет»;
5. через 5 и 20 секунд перепроверяет карточку и повторяет запись, если бизнес-процесс успел вернуть свою единицу.

Вторая и следующие карточки по этому семинару находят первую и получают номера из общего счётчика сами.

Номер в карточке перезаписывается, **только если документы по ней ещё не сформированы** — иначе номер уже в договоре, и менять его нельзя.

### Два поля номера в карточке «Семинаров»

| Поле | Роль |
|---|---|
| «Номер документа» | **источник**: из него печатается номер в договоре и счёте |
| «Номер текущего договора» | **след**: после формирования документов сюда копируется номер готового договора |

Исправленный номер приложение пишет в оба поля. До этого исправления оно писало только в «Номер текущего договора», и в договор уходила единица: так по два раза ушли договоры СН1910И-1 и СН1510О-1.

### Почему нет служебной карточки «Счётчик нумерации»

Раньше вместе с новым счётчиком приложение создавало в «Семинарах» служебную карточку с префиксом, чтобы бизнес-процесс нашёл по ней счётчик. Это не работало: нумератор запускается на любую новую карточку, стирает у неё префикс и вычисляет его заново из названий товаров. У служебной карточки товаров нет, префикс оставался пустым, и по префиксу она не находилась. Больше такие карточки не создаются.

## Что делать менеджеру

**Номер не выдался, приложение показывает ошибку.** Обновите страницу. Если повторяется — сообщите администратору: скорее всего Битрикс не отвечает или элемент списка занят чьим-то редактированием. Не формируйте документы без номера.

**Номер выглядит неожиданно большим.** Это нормально: номер продолжает общую последовательность по префиксу, а не нумерацию внутри сделки.

**В только что созданной карточке «Семинаров» стоит номер 1, а договоры по этому семинару уже были.** Подождите полминуты и обновите карточку: номер сменится на верный. Не формируйте документы, пока в поле «Номер документа» единица.

**Два договора с одинаковым номером.** Сообщите администратору с номерами обеих карточек. Такое возможно у префиксов, по которым исторически успели разъехаться счётчики.

## Что делать администратору

Проверить счётчик префикса: Компания → Списки → Договор, найти элемент с названием, равным префиксу.

**Признак проблемы — два элемента с одинаковым названием.** Оставить нужно тот, у которого значение «Номер» больше; второй пометить «Активен: Нет». Перед этим убедиться, что на него не ссылается ни одна карточка смарта полем `LIST_ID`.

**Второй признак — счётчик меньше номера, который уже стоит в документах.** Тогда следующий выданный номер повторит существующий договор. Счётчик нужно поднять до максимального фактически выданного номера.

Регулярная сверка делается скриптом аудита: он выгружает счётчики, смарт-процесс и сделки, ищет повторы «префикс + номер» и печатает названия посимвольно в кодах Unicode — так видно подмену кириллицы латиницей и невидимые символы.
