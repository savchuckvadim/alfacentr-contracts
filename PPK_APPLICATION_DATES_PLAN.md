# Приложение ППК: персональные даты, обязательные поля, крон

Анализ и план. Дата: 2026-08-21. Статус: **решения приняты; попутный фикс списков значений уже сделан, основная часть — к реализации**.

---

## 1. TL;DR

Для договоров ППК и Семинар+ППК генерируется «Приложение №1» — таблица, где строка = пара «участник × мероприятие». Требуется: обязательные ФИО, email и телефон у участника, персональные даты «с/по» у каждой пары, просмотр и правка всего этого в модалке перед отправкой, крон для актуализации дат и стадий.

**Хранение дат: JSON-поле на смарте участника** плюс служебное date-поле «дата начала следующего мероприятия». Не отдельный смарт (оверкилл) и не пары множественных полей (развалятся при первом редактировании).

Оценка: **21–30 ч ≈ 3–4 рабочих дня.** Блокирующих вопросов нет.

### Принятые решения

| Вопрос | Решение |
|---|---|
| Состав строки приложения | ФИО, почта, телефон, программа обучения, дата начала, дата окончания |
| Дата рождения, уровень образования, академические часы | Не выводим — шапку таблицы в шаблоне приводим в соответствие |
| Должность | Не нужна: поле не заводим, не требуем, не печатаем |
| Обязательные поля участника | ФИО, email, телефон + обе даты по каждой паре |
| Стадия при «до старта ≤ 14 дней» | Существующая «Подтверждён» — новых стадий в портале не создаём |
| «Пришёл / Не пришёл» | Только вручную, крон их не трогает |

## 2. Что показал анализ

### 2.1. Приложение ППК сегодня

- Генерация — локальный DOCX-шаблон `apps/back/storage/app/ppk/templates/ppk-application.docx` через docxtemplater. Шаблон наш файл, правим сами, не Битрикс.
- Строка = пара (участник × тема), собирается на фронте из распределения ППК, передаётся как `{index, fio, topic, date_start, date_end}`.
- **Шаблон уже требует больше, чем в него передают:** шапка колонки обещает «ФИО, Дата рождения, Уровень образования, Телефон, Адрес электронной почты», а рендерится только ФИО; колонка «Программа обучения, Объём (академических часов)» получает одно название темы. По принятому решению шапку упрощаем до фактического состава.
- **Даты берутся у первого товара темы** — то есть у всех участников одной программы они одинаковые, а при пустом поле молча уходит пустая строка. Персональные даты сегодня физически невыразимы.
- Строка не несёт идентификаторов участника, поэтому для редактирования связку надо добавить.
- Данные приложения на бэке **не валидируются** (написанный DTO мёртв), а ошибка рендера DOCX **глотается** — флоу продолжается без приложения.

### 2.2. Смарт «Участник» (1036, категория 26) — проверено по REST

- Поля: ФИО, телефон, email, комментарий, адрес для удостоверения, пять множественных полей программ, дни участия, формат, признак ППК, связки со сделкой. **Полей дат нет.**
- Стадии: Начало → Подготовка → Записан → Подтверждён → Пришёл / Не пришёл. **Их никто никогда не двигает:** участники создаются в «Начало» и остаются там навсегда, поэтому статистика по стадиям на фронте всегда пуста. Наш крон станет первым, кто их вообще меняет.
- Редактирование участника в модуле идёт без валидации (кроме непустого ФИО при создании).

### 2.3. Модалка перед отправкой

Существующая модалка подтверждения использует react-hook-form с проверкой на лету и уже реализует нужный паттерн обязательных полей (дата акта, банк, контактное лицо, email, телефон, комментарий ЕДО). Участников и ППК она не показывает; ширина рассчитана на узкую форму — под таблицу пар её придётся расширить.

### 2.4. Инфраструктура

- **Своей базы данных нет вообще:** ни ORM, ни контейнера, ни миграций (в конфиге висит мёртвый алиас на Prisma). Персистентность — Битрикс, Redis и файлы. Значит, даты хранить только в Битриксе.
- Крон: модуль планировщика подключён, но **ни одной задачи в проекте нет** — наша будет первой. Очереди и процессоры отработаны, авторизация фоновой задачи в портал решена готовым способом инициализации по домену.
- Бэк умеет обновлять смарты общим методом, фронт уже пишет поля участника напрямую — отдельный эндпоинт для сохранения дат не потребуется.

## 3. Где хранить даты пары «участник × мероприятие»

| Вариант | Разбор | Вердикт |
|---|---|---|
| **А. Пары множественных полей** «Даты с» / «Даты по» | Мероприятия участника размазаны по **пяти** разным множественным полям программ, единого упорядоченного списка не существует. Связь дат с мероприятиями по индексу развалится при первом же редактировании: удалили программу — индексы поехали, а Битрикс порядок множественных значений не гарантирует | Нет |
| **Б. Отдельный смарт «Участие»** | Чисто и видно в CRM, но: новая сущность, CRUD на обоих концах, синхронизация при каждом изменении программ, лишние запросы на отрисовку, каскадное удаление. Ради «правка в UI + крон + генерация» ничего не даёт сверх варианта В | Оверкилл |
| **В. JSON-поле на смарте участника** | Одно строковое поле: список пар «тема — дата с — дата по». Ключ связи — название темы, тот же текст, которым уже связаны распределение, товары и приложение. Атомарная запись, порядок не важен, одно чтение и одна запись, крону доступно обычным списком | **Выбрано** |

Минус варианта В — JSON не виден в фильтрах CRM. Компенсируем **служебным полем «Дата начала следующего мероприятия»** (тип «дата»): его пересчитывает крон, оно видно в карточке, по нему работают фильтры и роботы Битрикса. JSON — источник истины, дата — витрина.

Синхронизация JSON с программами участника — по названию темы: при открытии карточки или модалки мерджим сохранённое с актуальным распределением (новые темы появляются с пустыми датами, снятые исчезают), при сохранении пишем целиком. Гонок нет: JSON пишет только менеджер из интерфейса, крон трогает лишь дату-витрину и стадию.

**Новые поля смарта — два** (создаются по REST за минуты, права есть):

1. «Мероприятия ППК (служебное)» — строка, JSON пар;
2. «Дата начала следующего мероприятия» — дата.

Формат JSON — версионируемый, даты в ISO:

```json
{ "v": 1, "events": [ { "topic": "Название в заявке", "dateFrom": "2026-06-01", "dateTo": "2026-08-31" } ] }
```

## 4. План работ

### Блок A. Поля и общий пакет (2–2,5 ч)

Создать два поля смарта. В общем пакете: добавить их в перечисления полей участника, тип пары, хелперы разбора/сборки/мерджа JSON с юнит-тестами. Пересобрать пакет.

### Блок B. Модалка перед отправкой (7–10 ч) — ядро задачи

Для договоров ППК и Семинар+ППК в модалку добавляется секция «Приложение ППК»:

- таблица пар: участник, мероприятие, дата с, дата по (поля ввода дат), и по каждому участнику — ФИО, email, телефон с правкой на месте;
- источник пар — существующее распределение ППК, смердженное с сохранённым JSON;
- **обязательность**: кнопка отправки заблокирована, пока у каждого ППК-участника не заполнены ФИО, email и телефон, а у каждой пары — обе даты, причём «с» не позже «по». Подсветка ошибок — по образцу уже работающих полей модалки;
- предзаполнение дат из дат товара (именно они уходят в документ сегодня), менеджер их правит;
- по подтверждению — пакетное обновление участников (JSON и личные поля), затем штатная генерация.

Модалку под ППК-договоры расширяем до таблицы; для чистого семинара она остаётся прежней.

### Блок C. Карточка участника (2–3 ч)

В карточке «ППК программы» под каждой программой — два поля дат этой пары (тот же мердж и запись). Чтобы даты можно было готовить заранее, а не только в момент отправки.

### Блок D. Генерация приложения (3–4 ч)

Расширить строку приложения полями email и телефон (плюс идентификатор участника для трассировки); даты брать из JSON пары с откатом на даты товара. Обновить DOCX-шаблон: вывести телефон и email в первую колонку и **упростить шапку** до фактического состава — «ФИО, Телефон, Адрес электронной почты» и «Программа обучения». Включить настоящую валидацию входных данных приложения. Перестать молча глотать ошибку рендера — уведомление в сделку и в служебный канал (механика готова с прошлой задачи).

### Блок E. Крон (3–5 ч)

Первая запланированная задача в проекте, инфраструктура для неё уже стоит. Ежедневный прогон плюс ручной запуск эндпоинтом для проверки.

1. Выбрать участников активных стадий с непустым JSON, батчами.
2. Пересчитать «дату следующего мероприятия»: ближайшая дата начала не в прошлом; все прошли — очистить.
3. **Единственное правило стадий:** если до даты начала ближайшего мероприятия осталось 14 дней или меньше — перевести участника в «Подтверждён». Участников, уже находящихся в «Пришёл» или «Не пришёл», не трогать: это факт посещения, его отмечает человек. Других автопереходов не делаем.
4. Обновлять только изменившееся, сводка в служебный канал, ошибка одного участника не роняет прогон.

### Блок F. Тесты и сквозной прогон (3–4 ч)

Юнит-тесты на мердж и разбор JSON, пересчёт даты, правило 14 дней (в том числе границы: ровно 14 дней, прошедшая дата, участник в финальной стадии). Сквозной сценарий: ППК-сделка → модалка требует заполнения → заполняем → приложение с персональными датами и новыми колонками → ручной прогон крона → дата и стадия обновились. Регресс: чистый семинар (секции ППК нет), старые участники без JSON.

**Итого: 21–30 ч ≈ 3–4 рабочих дня.** Макет обновлённого шаблона согласуется с заказчиком отдельно.

## 4.1. Сделано попутно: списки значений не обновлялись (устранено)

**Симптом:** в таймлайне приёма заявки печаталось «Пакет УП: 26620» — голый идентификатор элемента вместо «Учетная политика 2027».

**Причина.** Приложение забирало поля сделки запросом со фильтром «SORT = 1». SORT — это порядок сортировки поля в карточке, а не признак «наше поле»; скорее всего, изначально имелась в виду сортировка, а получился фильтр. В результате из **613** полей сделки приложение видело только **95**. У всех остальных списки значений в рантайме не обновлялись, работали захардкоженные в коде — а там «Учетная политика 2027», добавленной в портале, разумеется, нет. Когда значение не находится в списке, в заявку и таймлайн уходит сырой идентификатор.

У поля «Пакет УП» SORT = 2, поэтому оно и не попадало в выборку. Проблема касалась не только его: «замороженными» оставались списки у трёх десятков полей-справочников.

**Что сделано.** Фильтр убран, и заодно устранён дорогой дозапрос: раньше на каждое поле шёл отдельный запрос за деталями (пачками, с паузами). Теперь два параллельных вызова — один отдаёт идентификаторы, типы и полные списки значений, второй названия полей. Итог: **613 полей вместо 95 примерно за одну секунду и два запроса** вместо полутора десятков.

Проверено на живых данных портала: значение 26620 теперь разворачивается в «Учетная политика 2027».

Затронутые файлы: сервис загрузки полей сделки, репозиторий и сервис Битрикс-сделки (добавлен метод получения описаний полей), схема типов. Мёртвая копия сервиса в `apps/back/src/apps/alfa` и одноразовые CLI-команды миграции полей не трогались — они вне рабочего пути.

## 5. Что не трогаем

Приём заявки, подбор товаров, распределение участников по товарам, генерацию остальных документов, тему письма, бизнес-процесс отправки. Расширяются только модалка, карточка участника и полезная нагрузка приложения ППК, плюс появляется крон.

## 6. Риски

1. **Ключ связи — текст названия темы.** Если менеджер переименует «Название в заявке» товара после сохранения дат, пара «отвяжется» и даты потеряются (тема исчезнет из мерджа как снятая). Смягчение: при мердже показывать в модалке предупреждение о темах, которые есть в JSON, но отсутствуют в текущем распределении, — не удалять их молча.
2. **Первый крон в проекте.** Планировщик подключён, но ни разу не использовался, поэтому в первый прогон закладываем ручной запуск и сводку в канал, а не «поставили и забыли».
3. **Изменение стадий увидят менеджеры.** Сейчас все участники стоят в «Начало»; после первого прогона часть уедет в «Подтверждён». Стоит предупредить команду до включения.
